## [LM-INCREMENTAL-1] When to add incremental parsing?

**Question**: Should we design for incremental parsing NOW (during semantic layer) or LATER?

### Option A: Design NOW (preemptive)
**Pros**:
- Avoid rework later
- LSP-ready from start

**Cons**:
- Adds complexity to semantic layer (already big scope)
- YAGNI - don't have LSP yet
- Risk: over-engineer for hypothetical use case

### Option B: Add LATER (when needed)
**Pros**:
- Focus on semantic correctness first
- Learn what we actually need from real usage
- Simpler initial implementation

**Cons**:
- Potential rework
- May discover architectural limitations

### Recommendation: **Staged approach** (hybrid)

**Stage 1-3 (Now)**: Design semantic layer WITHOUT incremental parsing
- Keep AST immutable (already doing this)
- Use spans (already have this)
- Side tables for semantic info (planned)

**Stage 4 (After basic semantic works)**: Evaluate incremental needs
- Measure: How long does full re-parse take on real files?
- Profile: Where is the bottleneck (lexer? parser? semantic?)
- Decide: Is incremental parsing actually needed?

**Stage 5 (If needed)**: Add incremental support
- Use existing spans for change detection
- Implement minimal incremental strategy

**Why staged**: We've proven incremental approach works (parser → spans → semantic). Don't over-invest before knowing actual needs.

## [LM-INCREMENTAL-3] Macro interaction (hard problem)

**Your question**: "Which sections can be safely cached vs. must always be re-expanded?"

**Answer**: This is THE hard problem for incremental + macros.

### Challenge:
```crystal
macro generate_methods(names)
  {% for name in names %}
    def {{name}}
      # ...
    end
  {% end %}
end

# If we edit ONE method, do we:
# A) Re-expand the entire macro? (safe, slow)
# B) Try to patch just one method? (complex, fragile)
# C) Cache expanded methods separately? (memory cost)
```

### Recommendation: **Defer to Stage 5**

**Why**:
1. We don't have macro expansion yet (Stage 6+ in semantic plan)
2. This is research-level complexity
3. Better to solve with real data

## [LM-INCREMENTAL-4] LSP workflow strategy

**Your question**: "Strategy for diffing tokens vs. lines"

### Current state:
```
Source file (Rope) → Lexer → Tokens → Parser → AST → Semantic
                                                        ↓
                                                  Diagnostics
```

### Incremental LSP flow (future):
```
Edit notification
  ↓
Calculate diff (line/offset ranges)
  ↓
Question: What needs re-processing?
  ↓
Option A: Re-lex/parse/semantic entire file (simple)
Option B: Identify changed AST nodes, re-process those (complex)
```

### Recommendation: **Start with Option A (full reprocess)**

**Evidence from other LSPs**:
- TypeScript: Re-processes entire file on edit (fast enough < 100ms)
- Rust Analyzer: Re-processes file, incrementally updates project graph
- Go: Re-processes file, caches package info

**Heuristic**: If full reprocess < 50ms, incremental not needed

**Measurement plan** (Stage 4):
```crystal
# Add timing to compiler
Benchmark.measure do
  lexer = Lexer.new(source)
  parser = Parser.new(lexer)
  program = parser.parse_program
  semantic = Semantic::Analyzer.new(program)
  semantic.analyze
end

# If < 50ms for 1000-line file → incremental not needed
# If > 200ms → consider incremental
```

## [LM-DAEDALUS] Risk: Premature optimization

**Red flag**: "Let's design for incremental parsing now"

**Why risky**:
1. **Unknown bottleneck**: Don't know if parse is slow yet
2. **Complexity explosion**: Incremental adds 50% more code
3. **Macro black hole**: Incremental + macros = research problem
4. **Distraction**: Delays semantic layer (actual current goal)

**Historical pattern**:
- Premature optimization is root of all evil (Knuth)
- Our session: Incremental approach worked (parser → spans → semantic)
- Industry: TypeScript didn't start with incremental, added later

**Mitigation**:
- **NOW**: Keep architecture incremental-friendly (already done)
- **STAGE 4**: Measure before optimizing
- **LATER**: Add incremental only if proven bottleneck
