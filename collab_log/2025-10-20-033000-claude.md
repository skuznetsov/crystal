## [LM-2] SEMANTIC_STAGES

**Crystal semantic analysis pipeline** (based on Crystal language semantics):

```
[LM-2.1] SYMBOL_COLLECTION
Input: AST (unresolved identifiers)
Output: SymbolTable (global scope populated)
Process:
  - Walk top-level nodes (class, def, macro definitions)
  - Register symbols in global scope
  - Don't resolve bodies yet
  - Handle reopening (classes can be defined multiple times)

[LM-2.2] NAME_RESOLUTION
Input: AST + SymbolTable
Output: AST with resolved IDs
Process:
  - Walk expressions
  - Resolve identifiers to symbols
  - Build scope hierarchy
  - Track local variables

[LM-2.3] TYPE_INFERENCE
Input: AST with resolved IDs
Output: Typed AST
Process:
  - Infer types bottom-up
  - Handle union types
  - Resolve method calls (overload resolution)
  - Type check assignments

[LM-2.4] MACRO_EXPANSION
Input: Typed AST + macro call sites
Output: Expanded AST
Process:
  - Execute macro interpreter
  - Substitute macro bodies
  - Re-run semantic passes on expanded nodes

[LM-2.5] VALIDATION
Input: Fully typed AST
Output: Validated AST or errors
Process:
  - Check exhaustiveness
  - Verify all types resolved
  - Validate method signatures
```

**Iterative nature**: Macro expansion may introduce new symbols → loop back to symbol collection

## [LM-3] DATA_STRUCTURES

### 3.1 Symbol Table

```crystal
class SymbolTable
  # Maps name → Symbol
  getter symbols : Hash(String, Symbol)
  getter parent : SymbolTable?

  def initialize(@parent = nil)
    @symbols = {} of String => Symbol
  end

  def define(name : String, symbol : Symbol)
    @symbols[name] = symbol
  end

  def lookup(name : String) : Symbol?
    @symbols[name]? || @parent.try(&.lookup(name))
  end
end
```

**Why**: Hierarchical scopes (global → class → method → block)

### 3.2 Symbol (unified representation)

```crystal
abstract class Symbol
  getter name : String
  getter node_id : ExprId  # Back-reference to AST

  abstract def type : Type
end

class MethodSymbol < Symbol
  getter params : Array(Param)
  getter return_type : Type
  getter body : ExprId?
end

class ClassSymbol < Symbol
  getter instance_vars : Hash(String, Type)
  getter methods : Array(MethodSymbol)
  getter superclass : ClassSymbol?
end

class VariableSymbol < Symbol
  getter declared_type : Type?
  getter inferred_type : Type
end
```

**Why**: Different symbols have different metadata

### 3.5 Semantic Context

```crystal
class SemanticContext
  getter symbol_table : SymbolTable
  getter type_arena : TypeArena
  getter current_scope : SymbolTable
  getter diagnostics : Array(Diagnostic)

  def push_scope
    @current_scope = SymbolTable.new(@current_scope)
  end

  def pop_scope
    @current_scope = @current_scope.parent.not_nil!
  end
end
```

**Why**: Thread context through all passes

**Minimal SymbolCollector**:
```crystal
class SymbolCollector
  def initialize(@program : Program, @ctx : SemanticContext)
  end

  def collect
    @program.roots.each do |root_id|
      visit(root_id)
    end
  end

  private def visit(node_id : ExprId)
    node = @program.arena[node_id]
    case node.kind
    when .macro_def?
      name = String.new(node.macro_name.not_nil!)
      symbol = MacroSymbol.new(name, node_id)
      @ctx.symbol_table.define(name, symbol)
    # ... handle other top-level definitions
    end
  end
end
```

  def resolve

      resolve_node(root_id)

## [LM-CASSANDRA] PATTERN_PREDICTION

**Historical patterns from similar compilers**:

### Pattern 1: Multi-pass architecture

**Evidence**: Most production compilers (GCC, LLVM, Rust, TypeScript)
- Pass 1: Symbol collection
- Pass 2: Name resolution
- Pass 3: Type inference
- Pass 4+: Optimization

**Prediction**: We'll need multiple passes, iterative refinement for macros

**Confidence**: 95%

### Pattern 2: Incremental scope

**Evidence**: Our session history
- Started with parser only
- Added spans incrementally
- Each feature fully tested before next

**Prediction**: Start with symbol collection only, validate thoroughly before type inference

**Success probability**: 90% (matches our proven pattern)

### Pattern 3: Macro complexity explosion

**Evidence**: Rust macros, C++ templates, Crystal macros
- Macros can generate arbitrary code
- Type checking after expansion is tricky
- Expansion order matters

**Prediction**: Macro expansion will be most complex part, leave for Phase 4+

**Risk**: High - may need architecture changes when we tackle macros

### Pattern 4: Union type challenges

**Evidence**: Crystal's union types are unique
- TypeScript has similar unions (structural)
- Crystal has union + nilable types
- Need efficient representation

**Prediction**: Union type normalization will need optimization

**Recommendation**: Start with simple types, add unions in Phase 3.5

## [LM-DAEDALUS] RISK_ANALYSIS

### Risk 1: Scope creep in semantic layer

**Symptom**: "Just add X while we're here"
**Danger**: Semantic layer is HUGE, could take months
**Mitigation**:
- Strict phase boundaries
- Each phase = 1-2 weeks max
- Validate before expanding
- Track scope in collab_log

### Risk 2: AST inadequacy

**Symptom**: "Need to restructure AST for types"
**Danger**: Invalidates parser work, breaks spans
**Mitigation**:
- Use side tables for semantic info (not AST modification)
- Only add AST fields if absolutely necessary
- Prove need with failing test first

### Risk 3: Macro expansion rabbit hole

**Symptom**: "Macros need interpreter, need runtime, need..."
**Danger**: Massive scope expansion, delays core type checking
**Mitigation**:
- Defer macros to Phase 4
- Start with non-macro code only
- Build macro story incrementally

### Risk 4: Overengineering type system

**Symptom**: "Need dependent types / HKT / GADTs"
**Danger**: Academic exercise, no practical value yet
**Mitigation**:
- Start with Int32, String, Bool
- Add features ONLY when needed by real code
- Pragmatic > perfect
